# 开发规范

## 权限

1. 远程连接服务器

你有一台服务器可以连接，命令是

```bash
ssh Guqq
```

已经通过公钥进行免密处理。服务器使用 slurm 作业调度系统，所有任务必须通过 slurm 提交，禁止直接在服务器上运行。

2. 许可操作

你应当使用 git 和 scp 来管理代码。

注意， git 操作自动批准使用，但不能一次删除所有文件。

- 本地：负责代码编辑、提交到github、从服务器上 scp 结果数据。

增、删、改、查， git push, git add, git commit, git clone, scp。注意，将大的数据文件（数据集、模型权重等） gitignore，避免上传到 github。如果一定需要上传大文件（如服务器网络不可用），请使用 scp 从本地传输。

- 服务器：查看集群情况、负责拉取代码同步、任务提交。

查看集群情况、查看代码、git pull 或 使用 slurm 系统 提交任务, 不得直接修改服务器上的文件。每次连接服务器前，必须在 docs/gpu.md 中记录连接用途，并检查是否在权限内；连接后，必须先执行 `git pull` 拉取最新代码，然后再执行任务。

- 网络：搜索资料、查找/下载文献、仓库、数据集、模型权重等。

注意：你可以在服务器上使用互联网下载必要的 libraries/packages/wheels。

## 开发规范

1. 进度更新

在推进过程中，在 docs/update.md 中记录每次进度更新，粒度按照 git commit 级别。

一开始在 state.md 中撰写计划，并随着任务进行的状况可以随时修改。在执行到 plan 的一个阶段时，更新 state.md ，并标注完成状态。

2. 单元测试

每次修改代码前，都要计划好与目标对应的单元测试。每次 git commit 后，都必须进行对应的单元测试。测试内容应当在 docs/test.md 中记录，测试结果也应当在 docs/test.md 中记录。

不得因测试失败而降低测试标准，除非有充分的证据说明测试与原来计划的要求不符。若连续5次无法修复，先在 docs/lessons.md 中查看是否有相关经验；若没有，考虑使用  git revert 回退到上一个 commit，并在 docs/lessons.md 中记录失败原因和经验教训。

3. 虚拟环境

在服务器上配置环境前，需要先使用 uv 创建虚拟环境，并在 docs/agents/env.md 中全面记录虚拟环境的创建、安装包、版本等信息，确保代码在不同环境下的可复现性。

4. 代码结构

在计划中，应当明确代码结构，划分模块，明确每个模块的功能和接口。每个模块应当有单独的文件夹，并在文件夹中包含 README.md 文件，说明模块的功能、输入输出、使用方法等。

5. 经验积累

在同一个任务连续失败3次后，必须在 docs/lessons.md 中查找失败原因和经验教训；若没有，则需要在 docs/lessons.md 中记录新的经验教训。包括但不限于：

- 网络连接经验
- 任务提交经验
- 代码调试经验
- 数据处理经验
- 模型训练经验
等。

另外，当涉及代码结构、功能、环境配置等方面经验时，应当在 docs/lessons.md 中记录，并在代码中添加注释，说明经验的应用。
